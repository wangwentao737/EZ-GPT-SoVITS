# GPT-SoVITS 整合包适配新手手册

这份手册带你适配一个 Windows 整合包，从选择文件夹开始，到在 GitHub 提交审核。第一次建议只登记 **引擎启动**和**一个你手头有配套权重的合成家族**。有把握后再逐项增加切片、转写和训练。

## 先准备这四样东西

1. **EZ 便携包。** 完整解压。里面有工作台 `EZ-GPT-SoVITS.exe` 和独立的 `EZ-Compatibility-Wizard.exe`。双击向导即可使用。
2. **目标整合包的副本。** 把完整整合包复制到一个专用目录，比如 `D:\EZ-adapt\engine-copy`。打开副本后，应能看到 `go-webui.bat`、`webui.py`、`runtime` 和 `GPT_SoVITS`。后面的启动和测试都用这个副本。
3. **合成素材。** 准备一对同一个声音、同一家族的 GPT `.ckpt` 和 SoVITS `.pth`，一段约 3 至 10 秒的干净 WAV，以及参考音频里实际说的文字。家族按权重提供者的说明填写，例如 `v5turbo`。再准备一句用于合成的短句。
4. **整理资料的文件夹。** 在副本外新建 `D:\EZ-adapt\review`。到提交 PR 时再使用自己的 GitHub 账号。

文中的目录是例子。你放在 E 盘时，把例子里的路径换成实际路径。若同一台机器已有工作台运行，请先结束任务并停止它管理的引擎。这样副本可以使用它的默认端口。

## 1. 用向导读出接口

- [ ] 双击副本的 `go-webui.bat`。等浏览器打开 WebUI，保留启动窗口。要验收合成，在 WebUI 的推理区选定配套权重，启用快速推理或并行推理，再打开推理 WebUI。不同整合包的按钮名称可能略有差别。
- [ ] 双击 `EZ-Compatibility-Wizard.exe`，在「整合包副本」选择刚才那个文件夹。
- [ ] 若打算提交 PR，在项目 GitHub 页进入 `compat/registry-v1.json`，把 `main` 上的文件下载到整理资料目录，再将它选为「基准清单」。首次练习可使用内置清单。
- [ ] 「对照的适配器」先选 `20261006`。准备的是 `0725-cu124` 时选同名适配器。点击「下一步 → 采集并核对」。
- [ ] 查看目标功能旁的结果。「可进入实际验收」说明接口和基础资源符合对照要求。仍需完成下一节的真实测试。

如果提示端口来自其他程序，请核对启动窗口中的整合包位置。快速推理未启动时，可以先记录主服务结果，稍后打开快速推理再采集。如果参数数量、顺序、返回值或资源路径仍不同，先保存差异，在下一阶段请维护者判断是否需要新适配器。手工修改登记清单无法解决接口不匹配。

向导会生成两个身份脚本的摘要，用来识别具体构建。启动 BAT 的摘要供核对，实际构建匹配使用 `webui.py` 与 `GPT_SoVITS/inference_webui_fast.py`。向导会把完整接口快照放在导出目录的 `capture-local` 里。

## 2. 导出本机测试清单

- [ ] 进入第三页，填写唯一的「整合包 ID」，比如 `gpt-sovits-20270115-cu124`。显示名称按发布页填写，公开来源填发布页链接或发包文件名。如果向导提示脚本已登记，请用它提示的现有 ID 更新该构建。
- [ ] 找到「引擎启动」和目标「语音合成 · 家族」两行。将这两项选为「待验收」。其他操作可以保持「不纳入」。
- [ ] 点「导出本机测试清单」，选择 `review` 文件夹。打开新生成的 `local-test-…` 子目录，找到 `registry-local-test.json`。

`registry-local-test.json` 会临时放行已经通过接口与资源核对的所选项。它用于独立的 EZ 测试数据目录。

## 3. 在工作台做一次实际验收

先关闭刚才手动启动的快速推理和 WebUI。接下来由工作台启动副本。保留向导窗口，等测试完成后还要回去填结果。

### 打开独立的测试数据目录

1. 用资源管理器打开 EZ 便携目录。在地址栏输入 `powershell` 并按 Enter。在打开的窗口粘贴下方一行。

   ```powershell
   & ".\EZ-GPT-SoVITS.exe" --data-root "D:\EZ-adapt\test-data"
   ```

2. 进入「设置」。在「文件位置」看一眼项目数据，应指向刚才指定的 `test-data`。
3. 在「整合包兼容清单」那一行点「导入清单」，选择 `registry-local-test.json`。
4. 点「添加启动路径」，选择副本里的 `go-webui.bat`。回到工作台，点「启动引擎」。看到可用状态后，打开「引擎详情」核对包 ID 和家族。

### 记录合成结果

1. 进「语音合成」，选择目标模型家族，点击「导入声音」。选两份权重，填参考 WAV、参考原文和语言，保存。
2. 输入短句，点「生成语音」。成功后播放整条 WAV，确认有声音且内容对应。记录任务号、家族、时长，能拿到的情况下记下种子和 WAV 的 SHA-256。工作台只在你主动生成时产生这条验收音频。
3. 在「任务记录」选中对应任务，通过「更多操作 → 复制结果」取得结果字段，在「产物或日志」定位文件。也可以在 PowerShell 中查看 WAV 摘要，把引号里的路径替换为实际文件。

   ```powershell
   Get-FileHash -Algorithm SHA256 -LiteralPath "D:\EZ-adapt\test-data\outputs\实际文件.wav"
   ```

如果失败，记录失败的步骤和任务提示。回到工作台打开启动日志，或在任务记录查看该任务的日志。缺资源就补齐后重测。接口不匹配时，把差异交给维护者。已有家族也应至少回归一条，确认更新清单后仍能使用。

## 4. 整理待审资料

1. 回到向导。在实际成功的行选择「通过」，填写任务号和结果。失败选「未通过」并填现象。尚未测试的保留「待验收」或选「不纳入」。同一构建已有正式结果时，「待验收」会沿用现有记录。
2. 点「导出待审资料」。新生成的 `compat-draft-…` 中有三份文件。

   | 文件 | 怎么用 |
   |---|---|
   | `registry-candidate.json` | 核对只修改目标包、修订号高于上游主分支。它是提交到 `compat/registry-v1.json` 的候选内容。 |
   | `acceptance-….md` | 验收报告。核对任务证据和局限后，按导出的文件名放到仓库的 `compat/`。 |
   | `PR-草稿.md` | 用作 PR 标题和说明，补上回归结果与需维护者确认的地方。 |

3. 再用一个空白数据目录导入 `registry-candidate.json`，确认已测试的家族可用、待验收的功能显示相应限制。检查报告引用指向即将提交的验收报告。
4. 提交前检查报告正文，只保留允许公开的信息。完整捕获目录、模型、录音、音频成品、数据库和详细运行日志留在本机。

## 5. 用 GitHub 网页提交 PR

这一节只需要浏览器和 GitHub 账号。

1. 打开 [EZ-GPT-SoVITS 原仓库](https://github.com/wangwentao737/EZ-GPT-SoVITS)，点击右上角 **Fork**，创建自己的副本。
2. 在你的副本中同步上游 `main`。在分支下拉框输入新分支名，例如 `compat/gpt-sovits-20270115-cu124`，选择从 `main` 创建新分支。后面的编辑都在这个新分支完成。
3. 进入新分支的 `compat/registry-v1.json`，点铅笔编辑。用待审候选清单中的完整 JSON 替换内容。在 **Commit changes** 中填写说明，例如「登记 GPT-SoVITS 20270115 合成兼容性」，提交到当前分支。
4. 回到 `compat` 目录用 **Add file → Upload files** 添加导出的验收报告。确认当前分支正确，再提交这一次修改。
5. 回到原仓库，点 **Pull requests → New pull request → compare across forks**。将 **base** 设为原仓库的 `main`，将 **head fork** 设为你的副本，**compare** 选刚创建的新分支。
6. 在 **Files changed** 核对清单和报告。把 `PR-草稿.md` 的内容整理到说明框，提交 PR。维护者提出修改时，继续向这个分支提交修正，PR 会更新。

页面英文按钮和分支方向可对照 [GitHub 从 fork 创建 PR 的说明](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request-from-a-fork)。

## 合入后与进阶操作

PR 合入后，回到目标版本工作台的「设置 → 整合包兼容清单 → 检查清单更新」，对照修订号，再看目标家族是否出现。若期间有别人的适配先合入，先重新取最新基准，把本次改动合入新的修订。

要登记训练、普通话或粤语转写、断点续训，按每个操作、家族和语种分别验收。遇到已有适配器都无法匹配的包，使用 [详细操作清单](adaptation-checklist.md) 和 [报告模板](registration-template.md) 整理接口差异后再评估代码修改。
